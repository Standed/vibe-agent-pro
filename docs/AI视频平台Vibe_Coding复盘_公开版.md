## 写在前面：这是我创业后的第一个「商业级」AI 视频平台

如果要用一句话概括这段经历，那就是：

> 我们用 AI 把产品做出来了，但真正决定效率上限的，仍然是“骨架”和“拆任务的能力”。

Video Agent Pro 目前主要用于内部生产与提效：从剧本拆解、分镜生成、图片批量生成到视频输出，我们把团队需要反复执行的流程“工具化 + 自动化”，让创作者可以更稳定地使用 Gemini、Sora、Vidu 等平台完成内容生产。

但这条路并不顺：MVP 在年前才真正能供团队使用，而 AI 视频生态已经迭代了很多轮。回头看，前期在架构与边界条件上想得不够“全”，导致相当长一段时间像在“打补丁”。AI 编程让实现速度变快，但并不会自动替你补上架构债——债还是要还，只是还的方式变了。

这篇文章希望把我们踩过的坑、收敛后的架构、以及我在 AI 编程工具链上的进化路径总结出来，让后来者少走弯路。

---

## 1. 我们到底做了什么：一个三视图、双模式的分镜到成片工作台

我们把影视创作流程拆成三个视图（也是三个“心智阶段”）：

```
故事构思（Planning） → 图片生成（Canvas） → 视频输出（Timeline）
```

并在 Canvas / Timeline 里做了一个关键交互设计：**Agent + Pro 双驱动**。

- **Agent 模式**：自然语言 → AI 自动选择工具与参数 → 批量操作、复杂编排
- **Pro 模式**：手动精调 → 参考图管理、参数复用、可控可回滚

这个组合的价值在于：**既能让新手“开口就能做”，也能让熟练用户“逐项可控”**。很多产品卡在“要么全自动、要么全手动”，而实际生产中两者都需要。

截至 v4.0.6，我们的系统规模大致是：

- **Agent 工具**：28 个（支持部分并行）
- **API 端点**：41 个（Next.js App Router / Serverless）
- **服务层**：22+ 个服务文件（推理、生成、任务、存储、计费等）
- **Hook 架构**：22 个自定义 Hooks（仅 Chat 相关就拆成了 12 个）
- **统一数据层**：`dataService.ts` 封装了大量 CRUD（便于迭代与收敛）

这些数字不是为了炫技，而是为了说明：当系统复杂度过了某个阈值，**“随手写、随手修”的 Vibe Coding 会越来越贵**。

## 2. 我们踩过的坑：为什么会进入「补丁地狱」

如果复盘最根本的原因，主要是三类“第一天就该想清楚”的硬约束，在早期被低估了。

### 2.1 Serverless 超时不是“性能问题”，是“架构边界”

早期我们把一些耗时链路放在一次请求里同步完成：轮询生成状态、下载并上传媒体、批量处理转存……最后都不可避免地撞上 Serverless 超时与不稳定。

后来的收敛方案很朴素：**双阶段异步化**。

- **轻量轮询层**：只更新数据库状态，毫秒级响应
- **重型执行层**：专门做下载/转存/重试，且强制小批量处理

这类拆分看起来“工程化”，但其实是把系统从“不确定”变成“可控”的必要条件。

### 2.2 `blob:` / `data:` 临时 URL 的问题，不是“偶发 Bug”，是“基础设施缺失”

如果把临时 URL 当成“能跑就行”的捷径，它迟早会变成：

- 刷新即丢、跨设备即丢
- 聊天历史媒体空白
- 分镜引用失效

最终我们做了**透明持久化**：任何本地临时媒体在写入业务模型之前，必须先固化到对象存储（如 R2），再用稳定 URL 回写。

这类机制一旦建立起来，后面无论引入多少模型、多少生成模式，都不会再重复踩同一个坑。

### 2.3 多提供商视频生成：状态管理必须“统一表结构 + 隔离状态机”

当系统同时接入多个视频提供商（不同参数、不同状态、不同回调），如果每家都单独一套表/一套状态逻辑，维护成本会指数级增长。

我们的收敛方向是：

- **统一任务表**：同一张任务表承载多 provider（`provider` 字段区分）
- **统一轮询与转存框架**：通用的任务状态同步 + R2 转存 + 失败重试
- **前端状态隔离**：不同模式/不同 provider 的参考图与配置必须隔离，避免“跨镜头污染”

## 3. 我真正学到的：AI 编程的瓶颈不在模型，而在“需求与任务的可执行性”

过去我也经历过很多“彻夜 Vibe Coding”的夜晚：AI 给了一段看似对的代码，但跑起来不对；修完又引入新的边缘 case；状态互相污染；最后变成反复打补丁。

当模型能力提升（尤其是能处理复杂项目上下文的那一档），我反而更清晰地意识到：

> 模型越强，越能暴露出“需求描述不够工程化”的问题。

你给一句“帮我做个视频生成功能”，AI 也许能产出一堆文件，但无法保证它满足你系统里那些隐含的约束：认证、计费、并发、重试、存储、状态隔离、回滚、观测……

### 3.1 从 Vibe Coding 到「收菜式」开发：一个更稳的节奏

我们后来更倾向于把开发流程改成三段式：

1. **深度设计（人主导）**：把架构边界、数据流、失败路径、验收标准写清楚
2. **自动实现（AI 主导）**：把任务拆到“无歧义可执行”，交给模型完成实现
3. **验收测试（人主导）**：次日 review + 测试 + 小范围灰度，问题回流到任务卡

这里的关键不是“AI 写代码”，而是“你交付给 AI 的任务是否可执行”。

### 3.2 拆任务的最小颗粒度：把不确定性压缩到任务卡里

下面是我们内部常用的一页式任务卡模板（你可以直接复用）：

#### 任务卡模板（建议直接复制）

- **目标**：一句话说明要解决什么问题（用户视角 + 系统视角）
- **输入**：依赖的现有模块/表结构/接口/约束（列出文件或接口名）
- **输出**：新增/修改哪些文件、暴露哪些 API、产生哪些数据变更
- **约束**：
  - 必须遵守的架构决策（例如：认证/积分必须走中间件）
  - 性能/超时/并发限制（例如：Serverless 不允许同步轮询）
  - 安全边界（例如：RLS、最小权限、禁止游客模式）
- **失败路径**：至少列 3 个常见失败场景以及期望行为（错误码/重试/回滚）
- **验收标准**：如何证明“完成了”（测试点、手动验收步骤、可观测指标）
- **回滚策略**：出现问题时如何安全回退（Feature Flag/保留旧路径/幂等迁移）

当你把任务拆到这个粒度，AI 的产出质量会明显上一个台阶：它不再“猜”，而是在执行。

## 4. 工具链进化：多模型协作不是追热点，而是“分工”

我们在项目中经历过几轮工具链变化，本质上不是“谁更强”，而是“谁更适合某类任务”。

一个更有效的方式是明确分工：

- **方案设计 / 架构评审 / 复杂 Debug**：更偏“推理与一致性”的模型与工具
- **前端 UI 细节 / 交互打磨 / Tailwind 细化**：更偏“审美与组件迭代”的模型与工具
- **大规模跨文件重构**：更偏“项目级上下文把控 + 工程落地”的工具

当你把模型当作“团队角色”而不是“万能助手”，协作效率会更稳定。

同时也要强调一句：工具再强，也无法替代你对系统的理解。**模型能加速实现，但无法替你做技术决策的责任人。**

---

## 5. 如果重来一次：我会在 Day 1 先做这 7 件事

这 7 件事不一定“最快”，但能极大降低后期返工概率：

1. **确定异步边界**：所有长链路默认异步化，任务表 + 轮询 + 重试从一开始就存在
2. **建立媒体持久化拦截**：任何临时 URL 进业务模型前必须固化
3. **统一任务模型**：多 provider 用统一任务表字段扩展，而不是平铺多张表
4. **认证与计费基线**：所有生成类 API 必经认证中间件 + 积分策略（包括二次确认）
5. **并发与队列**：把“限制并行”当成系统能力，而不是临时 patch
6. **观测与日志**：关键链路统一日志前缀、错误码、可追踪 ID，避免“出了事全靠猜”
7. **文档最小集**：至少一份架构总览 + 一份行为约束（给人看，也给 AI 看）

## 写在最后：AI 时代的工程能力，会越来越像“表达能力”

做完这个项目后，我最大的改变不是“代码写得更快”，而是更明确地知道：

- 一句需求要如何落到可执行的任务卡
- 一个系统要如何把不确定性隔离在边界之外
- 一套文档与约束要如何变成你和 AI 的“协作操作系统”
