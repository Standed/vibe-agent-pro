## 一、项目全貌：我们到底做了什么

### 1.1 产品定位

Video Agent Pro 是一个 **AI 驱动的影视分镜生成与编辑工具**。核心理念是：让视频创作者从剧本到成片，每一步都有 AI 辅助。

技术栈：
- **前端**：Next.js 15.1 + React 19 + TypeScript 5.8 + Tailwind CSS
- **后端**：Vercel Serverless + Next.js App Router（41 个 API 端点）
- **数据层**：Supabase PostgreSQL + Cloudflare R2（媒体存储）
- **AI 模型**：Gemini 3.1 Pro/Flash Image、Sora 2、Vidu、火山引擎 SeeDream/SeeDance、即梦

### 1.2 核心功能矩阵

整个产品覆盖了影视创作的三个阶段，对应三个核心视图：

```
故事构思 (Planning)  →  图片生成 (Canvas)  →  视频输出 (Timeline)
    剧本分镜拆解            无限画布+Grid生图         Sora/Vidu视频生成
```

每个视图都支持 **Agent（自然语言对话）+ Pro（精细参数控制）** 双驱动模式，这是我们在架构上的一个核心设计决策。

功能上，从剧本 AI 分镜、角色三视图生成、Grid 多视图分镜图生成、Sora/Vidu 视频批量生成，到完整的积分计费系统、角色一致性追踪、R2 媒体持久化管道……可以说该有的都有了。

### 1.3 规模感知——真实数据

- **服务层**：22+ 独立服务文件，涵盖 Agent 推理、图片生成、视频编排、任务管理等
- **数据层**：`dataService.ts` 一个文件封装了 **97 个方法**
- **Agent 工具**：28 个 Function Calling 工具，支持并行执行
- **Hook 架构**：22 个 Custom Hooks，仅 Chat 相关就有 12 个
- **Changelog**：从 v0.1 到 v4.0.6，累计 **30+ 个版本迭代记录**
- **文档体系**：`docs/` 目录下 30+ 份架构文档

这些数字背后，是无数个深夜的 Vibe Coding。

## 二、MVP 认知：你以为它"能用"就行了？

### 2.1 MVP 不是"最小可用"，而是"最小可验证"

这是我在这个项目里学到的最重要的创业认知之一。

很多技术出身的创业者（包括我自己）对 MVP 的理解是：快速做出来，能用就行。但这个理解是致命的——**"能用"不等于"能验证商业假设"。**

我的 MVP 年前才真正做出来供团队使用。但回头看，真正阻碍我的不是功能不够多，而是：

1. **没有想清楚 MVP 到底要验证什么**：是验证"AI 视频生产效率提升"？还是验证"分镜→成片全流程可行"？
2. **功能做得太多太杂**：一开始就想做完整的 Planning→Canvas→Timeline 三视图，结果骨架没搭好就急着做功能
3. **没有设定明确的验证标准**：怎么算"验证成功"？是用户用了还是用户效率真的提升了？

### 2.2 一个好的骨架胜过十个新功能

AI 视频行业已经迭代了很多轮，Sora、Vidu、即梦、可灵等平台能力在不断升级。**外部的变化越快，内部的骨架就越重要。**

我的项目在 MVP 阶段犯的核心错误就是——在还没有清晰的架构蓝图时，就急着做功能。结果就是后来花了大量时间打补丁。

**真正靠谱的 MVP 流程应该是：**

```
第一步：明确验证目标（2-3天）
  └── 这个 MVP 要回答什么问题？

第二步：设计核心骨架（1-2周）
  ├── 数据模型设计
  ├── API 接口契约
  ├── 状态管理方案
  ├── 部署架构方案
  └── 核心文档（README、AGENTS、开发规范）

第三步：填充最小功能集（2-3周）
  └── 只做能回答第一步问题的功能

第四步：内部验证（1周）
  └── 团队实际使用，收集反馈
```

如果能重来一次，我会把第二步至少延长到两周——**磨刀不误砍柴工，在 AI 编程时代尤其如此。**

### 2.3 MVP 阶段为什么骨架更重要？

因为 AI 编程的本质是：**你给 AI 的上下文越清晰、越结构化，它的输出质量就越高。**

一个好的骨架意味着：
- 清晰的目录结构 → AI 知道在哪里创建新文件
- 统一的编码规范 → AI 生成的代码风格一致
- 完善的类型定义 → AI 不会创造出冲突的类型
- 详细的文档体系 → AI 能理解设计决策的"为什么"

**没有骨架，AI 编程就像在沙滩上建城堡——建得越高，塌得越快。**

## 三、时间线：MVP 是怎么磨出来的

### 3.1 从零到 MVP（2025 年底 ～ 2026 年初）

| 版本 | 时间 | 里程碑 |
|------|------|--------|
| v0.1 | 2025-01 | 画布缩放、Gemini Grid 生成、AI 对话系统 |
| v0.2 | 2025-01 | 角色三视图、Grid 切片预览、音频上传 |
| v0.4 | 2025-12 | 用户认证、积分系统、云端存储、AbortController |
| v0.6 | 2025-12 | **Sora 视频生成全流程**：角色注册→场景拆分→Prompt 组装→任务提交→状态轮询→R2 持久化 |

这个阶段是最痛苦的。**节奏慢的原因很简单——没有一个好的骨架。**

### 3.2 补丁式迭代的至暗时期（2026 年 1 月）

这是我打补丁打得最多的一个月。看 Changelog 就知道有多密集：

```
v3.8.0 → v3.8.1 → v3.8.2 → v3.8.3 → v3.8.4 → v3.8.5 → v3.8.6 → v3.8.7 → v3.8.8 → v3.8.9 → v3.9.0 → ...
```

**每一个小版本号背后，都是一个坑：**

- **v3.8.2**：上传大图时 Vercel 报 413 错误，原来 4.5MB payload 限制卡住了 Grid 图片 → 不得不实现 R2 预签名直传
- **v3.8.5**：生产环境 `FUNCTION_INVOCATION_TIMEOUT`，发现即梦 API 是同步阻塞的 → 紧急改为客户端轮询
- **v3.9.0**：用户拖拽 Grid 切片到分镜后，刷新就丢了 → "所见即所得"的即时持久化重构
- **v3.9.3**：Vidu/Sora 的参考图状态互相污染 → 彻底重构为隔离 Hook 架构
- **v3.9.6**：Gemini 参考图在 VPN 下传不过去 → 实现 URL 优先+自动降级策略

**这些坑，90% 是因为前期架构设计不够深入导致的。**

### 3.3 架构收敛升级（2026 年 2 月）

经过一月份的"补丁地狱"，二月我下定决心做了几件大事：

1. **ChatPanel Hook 大重构**（v4.0.0）：把一个单体化的组件拆成 12 个独立 Hook
2. **Cron 异步架构**（v4.0.1）：将 Sora 状态检查和 R2 上传彻底解耦为两个独立定时任务
3. **事务原子性**（v4.0.1）：核心删除操作迁移到 PostgreSQL 存储过程，零数据不一致
4. **Hybrid Auth**（v4.0.4）：解决了困扰已久的登录状态水合延迟问题
5. **UI 设计体系**（v4.0.4-v4.0.6）：确立 Premium Glass 美学规范，去掉所有"AI 味"的廉价设计

这时候项目才算进入了一个相对健康的状态。

## 四、AI 编程工具进化史：从 Claude Code 到 Antigravity + Codex

这是我最想分享的部分。在整个项目开发过程中，我彻底进化成了一个深度使用 AI 编程的人。

### 4.1 早期：Claude Code 阶段

项目早期我主要使用 Claude Code（现已更名/迭代）。那时候的体验是：

- **优点**：理解上下文能力强，能直接操作文件
- **痛点**：生成的代码在复杂项目中经常出错，特别是跨文件引用和类型系统

那个阶段的 Vibe Coding 是真正的"彻夜"——经常凌晨 2 点还在跟 AI 反复调试一个参考图状态管理的 bug。

### 4.2 转折点：发现 Antigravity Tools

后来我开始使用谷歌的 **Antigravity Tools**，这是一个真正的转折点。

**为什么 Antigravity 这么好用？** 

核心原因是它很便宜且能接入多个顶级模型：
- **Claude Opus / Sonnet**：目前最强的代码理解和生成模型
- **Gemini 最新模型**：谷歌自家的大模型，对 Google 生态集成度最好

**我的双模型工作流**：

```
┌─────────────────────────┐     ┌─────────────────────────┐
│   Claude Opus/Sonnet    │     │   Gemini 最新模型        │
│   via Antigravity       │     │   via Antigravity       │
│                         │     │                         │
│   ● 方案设计与架构      │     │   ● 前端网页设计优化     │
│   ● 后端核心逻辑        │     │   ● UI/UX 细节打磨      │
│   ● 复杂 Bug 诊断       │     │   ● CSS/Tailwind 美化   │
│   ● 多文件重构          │     │   ● 组件交互优化         │
└─────────────────────────┘     └─────────────────────────┘
```

一个用来设计方案、写后端逻辑；另一个主要用于前端网页设计优化。这种分工让效率倍增。

### 4.3 终极武器：Codex（尤其是 3.3 Ultra High）

**Codex 的进化是肉眼可见的。** 到了 3.3 版本的 Ultra High 思考维度，在项目已经非常复杂（700+ 行的 README、750 行的 AGENTS.md、1600+ 行的 CLAUDE.md、41 个 API 端点、22 个 Hook）的情况下，它依然能够：

1. **深度理解意图**：告诉它"把 ChatPanel 的视频参考图状态解耦"，它能理解这涉及哪些文件、哪些 Hook、哪些状态流
2. **跨文件重构**：一次性修改 5-8 个文件，类型定义、import 路径、接口签名全部自洽
3. **保持上下文一致性**：在重构过程中不会丢失已有的业务逻辑

用客户端也会快很多，额度也基本够用（如果你适当使用的话）。

### 4.4 OpenClaw：强大但需要专业驾驭

必须提一下 **OpenClaw**。它目前非常强大，几乎是 AI 编程领域的"六边形战士"。但它的强大，背后需要使用者对 AI 编程相关的内容更加熟练，才能发挥到最强。

**OpenClaw 用好的前提条件：**

1. **你得会写好的 Prompt**：模糊的需求 = 模糊的代码。OpenClaw 放大你的能力，也放大你的弱点。
2. **你得有架构设计能力**：如果你连数据模型和 API 契约都没想清楚，再强的工具也救不了你。
3. **你得有代码审查能力**：AI 写的代码不是天然正确的。你至少要能判断它改了什么、影响了什么。
4. **你得有调试能力**：当 AI 写的代码跑出 bug，你要能定位问题，而不是盲目地让 AI "帮我修一下"。

**简单来说：AI 编程工具是放大器，不是替代品。** 你的底层能力有 80 分，AI 可以帮你放大到 150 分。你的底层能力只有 30 分，AI 最多帮你到 50 分，而且 bug 会更隐蔽。

### 4.5 我的实战工具推荐

**最佳实践组合：**

| 工具 | 用途 | 优势 |
|------|------|------|
| **Antigravity Tools + Claude Opus/Sonnet** | 方案设计、后端开发、复杂 Debug | 理解深度最强 |
| **Antigravity Tools + Gemini 最新** | 前端 UI 设计优化 | Google 生态整合好 |
| **Codex 3.3 Ultra High** | 复杂重构、多文件修改 | 项目级理解能力最强 |
| **OpenClaw** | 全能型日常开发 | 生态完善，社区活跃 |

**省钱技巧——我的真实操作：**

> 在闲鱼上多买几个 Google Pro 年会员账号，然后用 Antigravity Tools 接入使用。额度不够就切换账号。改 bug、解决复杂问题时切到 Codex，效果足够好，非常省心。

**关于国产 AI 编程工具的看法：**

老实说，一些国产模型在简单任务上速度确实快，效果也还不错。但是——**一旦项目复杂度上去了，能力就直线下降**。

当你的项目有 22 个 Hook、28 个 Agent 工具定义、41 个 API 端点、12 个聊天相关 Hook 之间有复杂的状态依赖时，国产模型很容易"断片"——它能理解单个文件，但无法理解文件间的关系网。

在 MVP 阶段、简单项目中用国产模型无可厚非。但如果你是做一个商业级别的完整平台，**我不建议把核心逻辑交给国产模型**。

## 五、血泪教训：测试是最不能省的环节

### 5.1 "改了一行代码，崩了三个功能"

我在这个项目里踩得最多的坑，不是架构设计的坑，而是**测试不充分**的坑。

真实案例：

- **v4.0.4** 优化了 `ChatBubble` 组件的性能（解耦 `useAuth` 上下文），结果把 `PlanningChat` 里的用户头像搞丢了——因为 Props 传递链断了
- **v3.9.1** 修复了即梦的 Pro Mode 显示问题，结果引入了一个登录死循环——因为路由守卫的逻辑被误改了
- **v3.8.5** 统一了 API 超时时间为 120 秒，结果 SeeDream 的生成接口开始频繁 timeout——因为它实际需要更长的时间

**每一次"好心的优化"引入的回归 bug，都比原来的问题更严重。**

### 5.2 测试的核心原则：改了什么，就全量测试什么

这不是说你要写 100% 的单元测试（虽然理想情况下应该）。而是说：

```
改了一个文件 → 测试这个文件所有相关的功能路径
改了一个 Hook → 测试所有使用这个 Hook 的组件
改了一个 API  → 测试所有调用这个 API 的前端流程
改了一个类型 → 运行 TypeScript 编译检查全量通过
```

**我的惨痛经验总结成一句话：你改了什么，一定要尽可能全量测试。不然新写的代码老是影响到系统原有正常的功能。**

### 5.3 我现在的测试清单

每次部署前，我会强制自己过一遍：

```markdown
## 部署前检查清单

### 编译层
- [ ] `npm run build` 零错误
- [ ] TypeScript 类型检查通过
- [ ] ESLint 无新增警告

### 核心功能回归
- [ ] 登录/登出流程正常
- [ ] 创建项目 → 分镜生成 → Grid 图片生成 → 应用到分镜
- [ ] Sora 视频生成 → 状态轮询 → R2 持久化
- [ ] Vidu 视频生成 → 各模式参考图正确
- [ ] Agent 模式：自然语言 → Function Calling → 结果同步到 Pro 模式
- [ ] Pro 模式：参考图管理 → 生成 → 历史记录

### 边界情况
- [ ] 刷新页面后所有数据完整
- [ ] 跨设备访问数据一致
- [ ] 取消正在生成的任务不报错
- [ ] 积分不足时有明确提示

### 视觉检查
- [ ] 暗色/亮色模式切换正常
- [ ] 大尺寸项目（50+ 分镜）不卡顿
- [ ] 移动端基本可用（无严重错位）
```

**这份清单看起来简单，但它阻止了我至少 10 次的生产环境事故。**

### 5.4 给 AI 写测试的技巧

让 AI 帮你写测试时，有个关键技巧：**不要让 AI 凭空写测试，要给它具体的边界条件。**

```markdown
# ❌ 错误的 Prompt
"帮我给 ViduService 写单元测试"

# ✅ 正确的 Prompt
"帮我给 ViduService.submitTask 写测试，覆盖以下场景：
1. 正常提交 img2video 任务，验证返回 taskId
2. 图片 URL 无效时抛出 Error('IMAGE_NOT_FOUND')
3. 积分不足时抛出 Error('INSUFFICIENT_CREDITS')
4. API 返回 429 时触发重试逻辑（最多 3 次）
5. 网络超时 30 秒后抛出 Error('TIMEOUT')"
```

**AI 写测试的质量，取决于你对边界条件的定义能力。**

## 六、核心反思：那些我应该更早想清楚的事

### 6.1 反思一：骨架先行，而非功能先行

我的 `ChatPanel.tsx` 最初是一个单体化组件，所有逻辑写在一起。随着 Vidu、Sora、即梦等视频提供商的加入，每个提供商都有不同的参考图管理逻辑：

- Vidu 有 img2video、start-end2video、reference2video 三种模式
- Sora 有角色注册、动态比例、智能拆分
- 每种模式下参考图的交互方式完全不同

**结果就是这个组件代码膨胀到几千行，状态互相污染，动一处牵万处。**

最后不得不花两周时间做大重构，拆出 12 个独立 Hook：

```typescript
// 重构前：ChatPanel.tsx 几千行全耦合
// 重构后：
hooks/chat/
├── useChatGeneration.ts      // 生成请求调度
├── useChatHistory.ts         // 历史记录管理
├── useChatScroll.ts          // 滚动行为
├── useChatActions.ts         // 操作回调
├── useChatModals.ts          // 弹窗状态
├── useChatReferenceInteractions.ts  // 拖拽/上传交互
├── useApplyVideoToShot.ts    // 视频应用逻辑
├── useAutoReference.ts       // @提及自动检测
├── useVideoModeReferences.ts // 视频模式参考图
├── useStartEndFrames.ts      // 首尾帧管理
├── useVideoReferences.ts     // 各模式独立参考图
└── useReferenceCallbacks.ts  // 参考图操作回调
```

**如果一开始就设计好这个分层结构，能省至少一半的时间。**

### 6.2 反思二：Serverless 的限制要从第一天就考虑

Vercel Serverless 的超时限制（Hobby 10s, Pro 60s）是一个硬约束。但我在早期完全没有意识到这一点，导致：

- Sora 视频生成在服务端等待轮询 → 超时
- 即梦 API 同步阻塞 60 秒 → 超时
- R2 上传在 Cron 任务中处理过多文件 → 超时

最后的解决方案是**双阶段异步架构**：

```
轮询层（check-sora-status）：毫秒级响应，仅更新数据库状态
执行层（retry-transfers）：处理实际的 R2 上传，批次控制在 5-10 个
```

这个架构如果从 Day 1 就有，能避免至少 5 个生产环境的紧急修复。

### 6.3 反思三：临时 URL 的持久化必须是底层基础设施

浏览器中的 `blob:` 和 `data:` URL 是临时的，刷新就没了。但在早期开发中，我经常直接把这些临时 URL 存到数据库里，结果就是：

- 用户生成了 Grid 图片，拖到分镜上看起来没问题，但一刷新页面就丢了
- 聊天历史里的图片在跨设备时全部变成空白

最终不得不实现一个**透明持久化机制**：

```typescript
// 任何 local URL 在赋值给数据模型之前，自动转为 R2 链接
const persistentUrl = await ensurePersistedImageUrl({ 
  url: localBlobUrl, 
  ...folderContext 
});
updateShot(shotId, { referenceImage: persistentUrl });
```

**如果一开始就有这个意识，可以避免大量的"图片丢失"类 bug。**

### 6.4 反思四：文档是你和 AI 协作的操作系统

到了项目中后期，我的核心文档体系长这样：

| 文档 | 行数 | 作用 |
|------|------|------|
| `README.md` | 700+ 行 | 项目全貌、功能列表、Changelog |
| `AGENTS.md` | 750 行 | AI Agent 的完整行为指南 |
| `CLAUDE.md` | 1600+ 行 | 开发哲学、技术标准、设计模式 |
| `docs/` 目录 | 30+ 文件 | 各子系统详细架构 |

**这些文档不仅是给人看的，更是给 AI 看的。**

当你用 Codex 或 Antigravity 做复杂重构时，AI 需要理解：
1. 项目的整体架构是什么
2. 哪些设计决策是刻意做出的（不应该"优化"掉）
3. 各模块的依赖关系

**文档越详细、越准确，AI 的输出质量越高。**

## 七、全方位规范体系：少走弯路的系统性保障

这是我最想给同行者强调的——**规范不是形式主义，而是防止你在复杂项目中迷路的导航系统。**

### 7.1 项目文档规范

| 规范 | 内容 | 我的实践 |
|------|------|----------|
| **README.md** | 项目概述、快速开始、功能列表、Changelog | 700+ 行，每个版本的变更逐条记录 |
| **AGENTS.md** | AI Agent 行为指南 | 定义了 28 个工具的使用规则和严禁行为 |
| **CLAUDE.md** | 开发哲学和技术标准 | 1600 行，包含"遇困 3 次后停止"等明确规则 |
| **架构文档** | 各子系统的设计决策 | `docs/` 下 30+ 分文档，涵盖认证、存储、视频编排等 |
| **CHANGELOG** | 每个版本的具体变更 | 每次发布必须更新，包含 ✅ 和 ⚠️ 标记 |

**关键原则：文档和代码同步更新，永远不要"先写代码，后补文档"。** 因为后补的文档，90% 会遗漏关键的设计决策。

### 7.2 设计规范

经过反复迭代，我们确立了 **"Film-Grade Black & White" + Premium Glass** 设计系统：

```
核心原则：
├── 色调：极致黑白灰 (Zinc)，让业务内容成为主角
├── 面板：Premium Glass（高斯模糊 + 极细内描边），弃用厚重阴影
├── 交互：hover 用细腻边框高亮，禁止发光阴影
├── 动效：Framer Motion 微小形变（active:scale-95）
└── 排布：严格 z-index 管理，悬浮层不遮挡核心内容
```

**设计规范的好处**：当 AI 帮你做 UI 时，它能严格按照规范输出，不会做出"AI 味"的廉价设计。

**反面教材**：早期没有设计规范时，不同功能模块的 UI 风格完全不统一——有的用 `shadow-lg`、有的用 `border`、有的用 `ring`，整个项目看起来像拼凑的。

### 7.3 代码编写规范

我们在 `CLAUDE.md` 中定义了明确的编码标准：

```typescript
// ✅ 命名规范
const GridPreviewModal = () => {};         // 组件：PascalCase
const handleGridGeneration = () => {};     // 函数：camelCase
const DEFAULT_TIMEOUT = 30000;             // 常量：UPPER_CASE
interface GridHistoryItem {}               // 类型：PascalCase

// ✅ 数据操作规范
import { dataService } from '@/lib/dataService';
await dataService.saveProject(project);    // 必须通过统一数据层

// ❌ 禁止直接操作底层
import { supabase } from '@/lib/supabase/client';  // 严禁！

// ✅ API 响应规范
import { apiSuccess, apiError } from '@/lib/api-response';
return apiSuccess(data);                   // 统一响应格式
return apiError('NOT_FOUND', 404);         // 统一错误格式
```

**最重要的规范**——我们列出了明确的"严禁行为"：

| 严禁 | 原因 |
|------|------|
| ❌ 客户端暴露 API Key | 安全风险 |
| ❌ 跳过白名单检查 | 权限控制 |
| ❌ 直接修改 `project.chatHistory` | 已迁移至 `chat_messages` 表 |
| ❌ 轮询使用同步阻塞 | Serverless 超时 |
| ❌ 存储 Base64 到 Supabase | 必须上传 R2 |
| ❌ Planning 模式调用生成工具 | 消耗资源 |

**"严禁清单"是约束 AI 行为的最有效方式。** AI 处理大型项目时偶尔会走捷径，明确的禁止规则能大大减少这种情况。

### 7.4 软件开发流程规范

```
需求阶段：
1. 明确输入、输出、边界条件
2. 不清晰的需求 → 提出澄清问题，不要假设
3. 搜索项目中是否已有类似实现

设计阶段：
1. 复杂任务拆解为 3-5 个 Stage
2. 记录在 IMPLEMENTATION_PLAN.md
3. 每个 Stage 有明确的成功标准

实施阶段：
1. 一次只改一个文件或一个小功能
2. 每步完成后确保编译通过
3. 遵循"类型定义 → Store Action → UI 组件 → 集成测试"的顺序

困难处理：
⚠️ 连续 3 次尝试失败后必须停止！
1. 记录失败原因
2. 研 2-3 个替代方案
3. 质疑根本假设——是否用了错误的抽象层级？
```

这套流程听起来像是教科书，但**它是我用血泪换来的**。尤其是"3 次尝试失败后停止"——我曾经在一个 bug 上死磕 6 小时，如果在第 3 次尝试后停下来换个思路，可能 30 分钟就能解决。

### 7.5 Git 版本管理规范

```
分支策略：
├── main          → 生产分支，只接受合并
├── dev           → 开发分支
└── feature/*     → 功能分支（从 dev checkout）

Commit 规范：
├── feat:    新功能
├── fix:     Bug 修复
├── refactor:重构（不改变行为）
├── docs:    文档更新
├── style:   样式/格式调整
├── perf:    性能优化
└── chore:   构建/工具链

合并规则：
├── feature → dev：Squash Merge（保持清晰的历史）
├── dev → main：Merge Commit（保留完整上下文）
└── 合并前：必须通过 build + lint
```

**真实教训**：有一次我直接在 main 分支上改代码，auto-deploy 把有 bug 的代码推到了生产环境。从此以后，我严格遵循分支策略——**main 分支只接受合并，永远不直接提交。**

### 7.6 发布与部署规范

```
发布前：
├── [ ] npm run build 零错误
├── [ ] 核心功能回归测试通过
├── [ ] 环境变量检查（新增的 key 是否配置）
├── [ ] CHANGELOG 已更新
├── [ ] 版本号已修改（README.md badge）

部署流程：
├── 代码合并到 main 后自动触发 Vercel 部署
├── 部署完成后检查 Vercel Dashboard 日志
├── 生产环境抽样测试核心流程
└── 确认无异常后，更新文档标记版本

回滚预案：
├── Vercel 支持一键回滚到上一次成功部署
├── 数据库 Schema 变更需可逆（含 Down Migration）
└── 环境变量变更需记录在 .env.example
```

## 八、创业认知：专业的事交给专业的人

### 8.1 不是所有事情都适合 Vibe Coding

这是我在创业过程中最大的认知升级之一。

我的团队除了 Video Agent Pro 之外，还有另一个系统（更偏传统业务逻辑，非 AI 原生）。那个系统的做法完全不同：**直接外包给专业团队**。

为什么？因为那个系统的核心不是 AI 创新，而是稳定的业务流程系统。它需要的是：

- 成熟的技术选型
- 标准化的系统设计
- 稳定可靠的交付质量
- 可维护的长期架构

**这些"无聊但重要"的事情，专业的外包团队做得比你 Vibe Coding 好 10 倍。**

### 8.2 外包的正确姿势

我们的外包合作模式是：

```
前期（外包团队主导）：
├── 需求文档：我们提供详细的业务需求
├── 技术方案：外包团队出设计方案，我们审核
├── 技术选型：前端框架、后端语言、数据库等由专业团队决定
├── 系统设计：数据库 ER 图、API 接口文档、架构图等
├── 开发实施：外包团队全程开发
├── 部署上线：外包团队负责初始部署
└── 交付验收：功能逐项验证

后期（我们自主运维）：
├── 日常运维：更新配置、处理异常
├── 紧急 Bug：结合 AI 编程工具快速修复
├── 小功能迭代：简单的增改需求自己用 AI 做
└── 大功能需求：评估后决定是否再次外包
```

**核心原则：前期让专业的人把架构做好，最多我们后续运维和结合 AI 编程解决一些紧急的 bug。**

### 8.3 哪些适合自己做，哪些适合外包？

| 维度 | 自己做（AI Vibe Coding） | 外包给专业团队 |
|------|--------------------------|----------------|
| **创新性** | AI 原生功能、探索性产品 | 成熟业务系统、标准化流程 |
| **变化速度** | 需求快速变化、频繁迭代 | 需求相对稳定、架构一次到位 |
| **核心竞争力** | 是团队核心竞争力所在 | 非核心但必须有的支撑系统 |
| **技术深度** | 你能驾驭的技术栈 | 你不熟悉但专业团队擅长的领域 |
| **团队人力** | 有人可以持续投入 | 人力不足或优先级不够 |

**Video Agent Pro 属于"自己做"的范畴**——它是 AI 原生的、需求快速变化的、是我们的核心竞争力。

但另一个业务系统属于"外包"的范畴——需求相对清晰、架构需要专业设计、我们的人力应该集中在 AI 视频这个核心方向。

### 8.4 外包项目的技术选型经验

外包项目的技术选型跟自己做差别很大：

| 因素 | 自己做 | 外包 |
|------|--------|------|
| **首选标准** | 你最熟悉的 | 市场成熟度最高的 |
| **框架选择** | 可以激进（Next.js 15, React 19） | 偏保守（稳定版本，LTS） |
| **部署方式** | Vercel/Serverless（灵活） | 标准云服务器（可控） |
| **维护考虑** | 自己能维护就行 | 要考虑后续接手成本 |

**关键教训**：外包项目一定要在合同里约定：完整的源码交付、部署文档、数据库设计文档、API 接口文档。**文档不全的交付=没交付。**

## 九、方法论升级：从 Vibe Coding 到"收菜式"开发

### 9.1 什么是 Vibe Coding？

Vibe Coding 就是——跟着感觉走，一边想一边做，遇到问题就修，修完继续做。

**它的优点是：启动快，适合探索期。**  
**它的缺点是：在复杂项目中，它是效率杀手。**

我的亲身体验：很多时候凌晨 2 点还在 Vibe Coding，跟 AI 反复调一个 bug，调到 4 点终于修好了。但第二天发现这个修复引入了新 bug……

### 9.2 "收菜式"开发：AI 编程的正确姿势

当 AI 编程模型不断进步（尤其是 Codex 3.3 Ultra High 这个级别），我们需要反省自己——**是不是方式不对？**

正确的方式应该是：

```
阶段一：深度设计（人类主导，AI 辅助）
├── 架构蓝图
├── 功能细节文档
├── 技术方案评审
└── 任务拆解（拆到足够细）

阶段二：自动实现（AI 主导，人类审核）
├── 把拆好的任务交给 Codex / Antigravity
├── 每个任务包含清晰的输入、输出、约束
├── AI 按方案执行，产出代码
└── 人类不需要盯着，可以去做其他事

阶段三：验收测试（人类主导）
├── 第二天来"收菜"—— 看 AI 产出的代码
├── 全量回归测试（关键路径 + 受影响模块）
├── 人工 review 关键逻辑
└── 发现问题 → 细化需求 → 回到阶段二
```

**简而言之：如果我们把架构和功能细节设计得更详细一些，就能让 AI 按照详细方案去自动实现。我们只需要拆得足够细致，然后让它执行，第二天再来"收菜"，然后去测试即可。**

### 9.3 "拆任务"的艺术

这里的关键是——**任务要拆到什么粒度？**

以我项目中的一个真实案例为例：

**❌ 错误的拆法（太粗）：**
> "实现 Vidu 视频生成功能"

**✅ 正确的拆法（足够细）：**

```
任务 1：扩展 sora_tasks 表（增加 provider 字段）
  - 输入：现有表结构
  - 输出：支持 sora/vidu/jimeng 的统一任务表
  - 约束：不影响现有 Sora 查询

任务 2：创建 ViduService.ts
  - 输入：Vidu API 文档
  - 输出：封装 submit/status/cancel 方法
  - 约束：遵循 KaponaiService.ts 的代码风格

任务 3：创建 API 路由 /api/vidu/generate
  - 输入：参考 /api/sora/generate 的模式
  - 输出：POST 端点，auth-middleware 认证 + 积分扣除
  - 约束：使用 api-response.ts 标准化响应

任务 4：创建 useViduGeneration Hook
  - 输入：参考 useSoraGeneration 的模式
  - 输出：封装生成流程 + 轮询状态 + R2 持久化
  - 约束：使用 TaskQueueService 控制并发
```

**当任务拆到这个粒度，Codex 3.3 Ultra High 基本可以一次性搞定。**

### 9.4 "收菜"的标准动作

"收菜"不是随便看看就完事了。我现在的标准动作是：

```
1. 查看 diff：AI 改了哪些文件？每个文件改了什么？
2. 编译检查：npm run build 是否通过？
3. 逻辑审查：核心业务逻辑是否符合预期？
4. 边界检查：异常情况处理是否完善？
5. 风格检查：代码风格是否符合项目规范？
6. 测试跑通：被修改模块的全量功能测试
7. 关联检查：修改是否影响了其他模块？
```

## 十、架构设计中的关键决策

### 10.1 Agent + Pro 双驱动

这是整个平台最核心的交互设计：

| 模式 | 特点 | 适用场景 |
|------|------|----------|
| **Agent 模式** | 自然语言→AI 自动选择工具和参数 | 快速迭代、批量操作 |
| **Pro 模式** | 手动控制每一个参数 | 精确调整、参考图管理 |

两个模式共享分镜数据，Agent 操作的结果会自动同步到 Pro 的聊天历史（通过 `metadata.source = 'agent_sync'` 标记）。

### 10.2 统一视频任务表

早期 Sora 任务用单独的表。后来引入 Vidu、即梦视频后，我们选择统一——在 `sora_tasks` 表增加 `provider` 字段：

```sql
provider: 'sora' | 'vidu' | 'jimeng' | 'volcano' | 'runway'
```

**好处是巨大的**：
- 所有任务的状态轮询、R2 转存、失败重试逻辑可以复用
- 后续新增视频提供商只需要增加一个 provider 值
- 管理后台只需要维护一套界面

### 10.3 三级聊天历史

```
Project 级别 → Planning 阶段的对话
Scene 级别  → 场景级 Grid 生成历史
Shot 级别   → 单个分镜的 Pro 模式对话
```

### 10.4 积分系统的二次确认机制

AI Agent 最怕的就是"一句话烧光积分"。我们实现了前置拦截：

```
用户发指令 → Agent 预检意图 → 积分预估 → UI 弹窗确认 → 同意后才执行
```

甚至考虑了模型"抽风"的情况——如果模型跳过 ToolCall 直接回复文本，中间件会自动检测并阻止虚假执行。

### 10.5 技术选型的"为什么"

| 选型 | 选了什么 | 为什么不选别的 |
|------|----------|----------------|
| **部署** | Vercel | 全球 CDN、自动扩展、Preview 部署。不选自建服务器是因为创业早期运维能力有限 |
| **数据库** | Supabase | 托管 PostgreSQL + Auth + Realtime 一站式。不选 Firebase 是因为 PostgreSQL 更灵活 |
| **文件存储** | Cloudflare R2 | 零出口费用。不选 S3 是因为视频预览流量大、S3 出口费用高 |
| **前端框架** | Next.js 15 | App Router + API Route 全栈一体。不选 Vite 是因为需要 SSR 和 API 路由 |
| **状态管理** | Zustand + Immer | 轻量灵活。不选 Redux 是因为 overhead 太大 |
| **CSS** | Tailwind CSS | 与 AI 编程配合好，AI 能直接写 utility class。不选 CSS Module 是因为 AI 生成效率低 |

## 十一、给 AI 视频创业者的建议

### 11.1 开发节奏

1. **第一周**：不写代码。画架构图，写技术方案文档，定义数据模型
2. **第二周**：搭骨架。核心服务接口、API 路由结构、数据库 Schema
3. **第三周起**：按优先级填充功能
4. **始终保持**：文档和代码同步更新，每次部署前全量回归测试

### 11.2 必须从 Day 1 就考虑的事

- [ ] **Serverless 超时限制** → 所有耗时操作异步化
- [ ] **临时 URL 持久化** → 底层拦截机制
- [ ] **多提供商支持** → 统一任务表、统一状态管理
- [ ] **认证与积分** → 从架构层保证，不是后面"加上去"
- [ ] **错误监控** → Sentry 或 LogRocket，主动发现问题而非被动等用户反馈
- [ ] **Git 分支策略** → main 只接受合并，永远不直接提交
- [ ] **文档体系** → README + AGENTS + 开发规范，第一天就建立
- [ ] **设计规范** → 颜色、字体、组件样式、间距、动效，统一定义

### 11.4 创业心态

1. **不要什么都自己做**：你的时间是最稀缺的资源，核心创新自己做，标准化系统外包
2. **不要追求完美的 v1**：先验证商业假设，再追求技术完美
3. **不要轻视规范**：越复杂的项目，规范节省的时间越多
4. **不要忽视测试**：生产环境的 bug 修复成本是开发环境的 10 倍
5. **不要独自苦熬**：AI 编程模型在不断进步，彻夜 Vibe Coding 更可能是方式不对，而不是你不够努力

## 十二、写在最后

回顾这段旅程，我从一个"知道 AI 编程怎么回事"的人，进化成了一个"深度依赖 AI 编程完成商业级项目"的人。

核心感悟有五点：

**1. AI 编程的效率瓶颈不在 AI，而在你的需求描述能力。**

Codex 3.3 Ultra High 已经足够强了。但如果你给它一句"帮我做个视频生成功能"，它不可能做出你想要的东西。你需要把需求拆到"任何一个合格的程序员都能无歧义执行"的粒度。

**2. 架构设计的时间投入，ROI 是最高的。**

我花一两个月打补丁走的弯路，如果用两三周来做架构设计，可以完全避免。前期感觉"设计"比"写代码"慢，但长期看它是最快的路。

**3. 文档是你递给 AI 的说明书，说明书越好，产出越好。**

我的 AGENTS.md（750 行）和 CLAUDE.md（1600 行）不是废话堆砌，而是经过反复打磨的"开发哲学 + 技术约束 + 设计决策"的结晶。每次新功能开发，AI 读了这些文档后，产出的代码就像是项目原生的一样。

**4. 测试不是可选项，是生命线。**

改了什么就全量测试什么。我因为"觉得只是小改动"跳过测试而引入的生产环境 bug，远比我因为"功能没做完"而延迟发布造成的损失更大。

**5. 专业的事交给专业的人。**

别什么都自己做，别什么都 Vibe Coding。AI 编程让你能做更多事，但不意味着什么事都该你做。把非核心系统外包给专业团队，你的时间和精力应该放在核心竞争力上。
