## 0. 一句话总结

我们不是“把功能做出来了”就结束了，而是经历了：**探索期的 Vibe Coding → 补丁地狱 → 架构收敛 → 文档驱动 + 任务卡驱动的收菜式开发**。

最重要的收获是两条：

1. **Serverless、媒体持久化、多提供商任务管理**这三件事，必须从 Day 1 当作“平台基础设施”对待。  
2. AI 编程时代，速度瓶颈往往不在模型，而在我们能否把任务拆到“无歧义可执行”，并把隐含约束写成显式规范。

## 1. 我们做了什么：三视图 + 双模式的创作工作台

产品流程被拆成三个视图（对应三种上下文与数据粒度）：

```
Planning（故事构思） → Canvas（图片生成/编排） → Timeline（视频输出/预览）
```

其中 Canvas / Timeline 支持 **Agent + Pro 双驱动**：

- **Agent 模式**：自然语言触发工具编排，适合批量、复杂任务（例如“生成场景 3 的全部分镜图”“分镜 14-16 用 Sora 生成”）。
- **Pro 模式**：参数与参考图精调，适合稳定生产与复用（尤其是参考图体系、首尾帧、跨分镜隔离等）。

对应到代码层，最核心的“业务交互密度”集中在：

- Pro 模式 UI：`src/components/chat/ChatPanel.tsx`
- Pro 模式 Hooks：`src/hooks/chat/*`
- Agent 面板：`src/components/agent/*`
- 认证与积分：`src/lib/auth-middleware.ts`
- 统一数据服务：`src/lib/dataService.ts`
- Sora/Vidu 任务与转存：`src/app/api/sora/*`、`src/app/api/vidu/*`、`src/app/api/cron/*`

我们最终形成的“平台级能力”包括：

- 多模型图片生成（单图 / Grid / 编辑 / 分析）
- 多提供商视频生成（Sora / Vidu / 火山等）与统一任务表
- R2 媒体持久化与失败重试
- 积分预估 + 二次确认（防止一句话烧光积分）
- Hybrid Auth（绕过 session 水合延迟，稳定登录体验）
- 数据删除等高风险操作的数据库级原子性（RPC/存储过程）

## 2. 时间线（内部视角）：我们如何从“能跑”走到“可维护”

为了避免“版本号很酷但读不懂”，内部复盘更关注阶段性转折点：

### 阶段 A：探索期（先跑起来）

特征：目标是验证“从剧本到分镜再到视频”的闭环可行性；允许短期技术债。

- 画布、基础聊天、图片生成、Grid、多视图拼接等能力先跑通
- 早期大量逻辑堆在组件里，尤其是 Pro 模式主面板

### 阶段 B：补丁地狱（债务爆炸）

典型症状：

- 生成链路从“单一提供商”变成“多提供商 + 多模式”后，状态互相污染
- Serverless 超时开始变成真实生产事故
- 临时 URL（`blob:`/`data:`）导致“刷新就丢”“跨设备全空白”

这一阶段的本质是：我们把“平台基础设施”当作“功能细节”来做，结果被边界条件反复教育。

### 阶段 C：架构收敛（把平台基础设施补齐）

我们在这个阶段做了几次关键收敛，后面每一次迭代成本明显下降：

1. Pro 模式拆 Hook（从单体到可组合）
2. Cron 双阶段异步化（把超时风险从请求链路移出去）
3. 事务原子性迁移到 DB（避免级联数据不一致）
4. Hybrid Auth 稳定登录（减少用户侧“看起来没登录/闪烁”）
5. Premium Glass 设计规范（避免 UI 风格漂移与“AI 味”）

## 3. 三个“我们应该更早做对”的基础设施

### 3.1 Serverless：不要在一次请求里做完“长链路”

最早我们踩的是典型坑：把“轮询 + 下载 + 上传 + 写库”塞到一条 API 路由里，结果就是：

- 请求超时、重试放大、状态不一致
- 用户侧看到“生成失败”，但实际上可能生成完成了，只是我们没及时固化

后来的稳定做法是 **双阶段异步架构**（把链路拆成两种不同 SLA 的任务）：

- **轻量轮询**：快速查询提供商状态，只负责更新 DB（快、幂等、可频繁跑）
- **重型转存**：只处理少量 `pending_upload` 任务，做实际下载与 R2 上传（慢、受控、可重试）

这个策略的工程价值在于：即使某次重型任务失败，也不会影响“状态推进”，系统可以在下一轮 cron 继续补偿。

### 3.2 临时 URL：必须“透明持久化”，不允许写进业务模型

从产品视角，“拖一张图到分镜”看起来成功了，但如果那张图其实还是 `blob:`，那它只是**当前浏览器会话的幻觉**。

我们最后把它提升为平台原则：

- **任何** `blob:` / `data:` 等临时 URL，在写入 Scene/Shot 的引用字段之前，必须先固化到 R2，并回写稳定 URL。

把这条原则变成拦截器/工具后，后续无论 Grid 切片、聊天历史图片、拖拽进画板的预览图，都不会再出现“刷新丢失”类问题。

### 3.3 多提供商：统一任务模型 + 隔离状态机

一旦接入 2+ 提供商，多数系统会在 3 个地方失控：

1. 任务表结构平铺（A 一张表，B 一张表，后面全是胶水）
2. 状态轮询逻辑复制粘贴（小改即错）
3. 前端引用状态串线（切换分镜污染下一镜头）

我们更倾向的收敛方式是：

- **统一任务表**：同一张任务表承载多个 `provider`
- **统一轮询框架**：批量轮询 + 状态 Map 缓存
- **前端引用隔离**：不同分镜、不同视频模式（img2video / start-end / reference2video）各自独立状态（切换分镜必须 reset）

## 4. Pro 模式的教训：复杂交互必须“拆 Hook”，否则一定炸

最典型的“补丁地狱核心”发生在 Pro 模式主面板：随着参考图体系、首尾帧、拖拽上传、历史加载、分页滚动、视频模式切换逐步叠加，如果继续把逻辑堆在一个组件里：

- 闭包陷阱导致“删除失效”
- effect 之间互相触发，状态不稳定
- 切换分镜带来跨镜头污染
- 新功能每加一次，都要担心破坏旧逻辑

我们最后选择的正确方向是：**把状态与副作用拆成职责明确的 hooks**，并把“参考图交互”集中到一个地方。

内部建议的判断标准：

- 只要一个组件里出现 3+ 类“相互独立但互相影响”的副作用（历史加载 / 媒体加载 / 滚动 / 引用同步 / 模式切换），就应该拆。
- 任何“拖拽/上传/引用列表”的交互，都应该有单独的交互层 hook（可测、可替换、可复用）。

## 5. 积分与 Agent：一句话烧光积分是“必须预防”的产品事故

Agent 模式带来的效率也带来了风险：用户一句“把所有分镜都生成视频”，可能意味着数千积分与长时间排队。

我们最终的安全策略是“**预估 → 拦截 → 二次确认 → 才执行**”，并考虑了模型可能“跳过 ToolCall 直接文本回复”的异常路径，避免虚假执行与隐式扣费。

内部复盘结论：

- 积分系统不是“计费模块”，而是“平台安全模块”
- 二次确认不是“弹窗”，而是“幂等与一致性的一部分”

## 6. 文档：它不是“写给人看的”，更是“写给 AI 和未来的自己看的”

当项目进入多模块、多 provider、多状态机并行演进之后，文档的重要性会发生质变：它开始像“操作系统”一样决定协作效率。

对我们来说，至少需要三类文档长期保持可用：

1. **架构全貌与核心约束**：哪些是刻意决策，哪些禁止“顺手优化掉”
2. **子系统细节**：Pro 模式、任务表、Cron 异步、认证与积分、存储与持久化
3. **AI 协作指南**：当我们把任务交给模型时，需要哪些输入与约束

我们在后期明显感受到：当文档够完整时，AI 的产出会更“像项目原生代码”，而不是“拼接产物”。

## 7. 我个人的 AI 工程化工作流：从彻夜调试到隔天收菜

我早期的典型模式是“边写边改边调”，这在探索期有价值，但一旦系统复杂，后期成本非常高。

更有效的方式是把 AI 当成“执行引擎”，而不是“灵感伙伴”：

### 7.1 一页任务卡（工程可执行）

内部推荐把任何“要改 3 个以上文件的需求”写成任务卡（最少包含）：

- 目标（用户价值 + 系统目标）
- 输入（现有文件/模块/约束）
- 输出（要改哪些文件/接口/表字段）
- 约束（认证/积分/超时/并发/存储原则）
- 失败路径（至少 3 个）
- 验收标准（具体到按钮/接口/日志/数据）

### 7.2 先设计再实现（把不确定性前置）

当任务卡写清楚后，把实现交给 AI，次日来做三件事：

1. Review 是否遵守约束（尤其 auth/credits/storage）
2. 跑关键路径（生成、轮询、转存、历史加载）
3. 观察日志与失败路径（是否可重试、是否幂等）

这就是我们说的“收菜式”——不是偷懒，而是把注意力放在**验收与决策**上。

## 8. 给团队的落地建议（可执行清单）

### 8.1 Day 1 就要定死的 7 条原则

- [ ] 长链路默认异步化；请求里禁止同步轮询 + 转存
- [ ] 临时 URL 禁止写入业务模型；必须先持久化再引用
- [ ] 多 provider 统一任务表；轮询与转存框架复用
- [ ] 生成类 API 统一走认证 + 积分；Agent 必须二次确认
- [ ] 并发必须可控（队列/批处理）；不要靠“运气”跑通
- [ ] 关键链路日志标准化（前缀/错误码/traceId）
- [ ] 文档优先：架构约束写清楚，避免后期反复“解释给 AI 听”

### 8.2 我们最常见的返工来源（请优先避免）

- “先写再说”的同步实现（最终都要拆成异步）
- “先存 blob URL”的临时方案（最终都要补持久化）
- “先写在组件里”的交互逻辑（最终都要拆 hook）
- “先别管积分”的体验优化（最终都要补安全与一致性）

## 写在最后

这次复盘最想传递的不是“我们用了哪些模型”，而是一个更确定的工程结论：

> **AI 让实现更快，但让系统变稳的，仍然是架构边界、约束显式化、以及任务拆解能力。**

后续如果要继续迭代（引入更多 provider、更复杂的参考图策略、更强的批量编排），我们应该把“平台基础设施”持续保持在第一优先级：它直接决定我们是继续高速迭代，还是再次掉进补丁地狱。
